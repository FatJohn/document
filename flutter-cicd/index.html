發版 / 派發閘門

只有 tag 會派發，而且 tag 與分支必須配對

推分支、開 PR、手動觸發都只跑測試與建置。一個專職的 job 是唯一的開關，它同時驗兩件事。

條件一 / tag 格式對

dev 線
^dev[0-9]+\.[0-9]+\.[0-9]+(-[0-9]+)?$

prod 線
^v[0-9]+\.[0-9]+\.[0-9]+(-[0-9]+)?$

條件二 / tag 真的在那條線上

用 git merge-base --is-ancestor 確認 tag 指向的 commit 是 origin/staging（或 origin/main）的祖先。

在 main 推 dev tag、或在 staging 推 v tag，會建置成功但跳過派發。

# 兩個條件都成立才輸出 should_deploy=true，兩個 deploy job 都掛這個條件
if: needs.check-deployment-eligibility.outputs.should_deploy == 'true'

發版 / 結構

重複的步驟都抽成 composite action

兩條 CI 線共用同一組 action，環境差異只用 inputs 表達，所以流程只有一份。

composite action做什麼關鍵 inputs
test格式檢查、靜態分析、單元測試—
build-number產生建置編號environment, persist
build-android建 APK，需要時建 AABenvironment, build_aab
build-ios簽章並建 IPAenvironment, 憑證
deploy-firebaseAPK 上 App Distributionenvironment, artifact_name
deploy-testflightIPA 上 TestFlightenvironment, artifact_name
setup-submodules用 deploy key 拉私有 submoduledeploy-key
cleanup-ssh收尾清掉 SSH key—

action 之間也能疊：三個 action 開頭都先呼叫 setup-submodules，結尾呼叫 cleanup-ssh。

發版 / token

為什麼推 tag 需要 App token

目的 用內建 GITHUB_TOKEN 推的 ref 不會觸發任何 workflow，這是 GitHub 的防遞迴規則。tag 推上去卻叫不動 CI，發版就斷在那裡。
做法 用 GitHub App 的 Client ID 與 private key 簽出 installation token，有效一小時、job 結束自動撤銷，再用它 checkout 與 push tag。
不用個人 PAT PAT 綁人、會過期、人離職就壞，而且在 PR 上看起來像那個人做的。 
- uses: actions/create-github-app-token@v3
  id: app-token
  with:
    client-id: ${{ secrets.RELEASE_APP_ID }}
    private-key: ${{ secrets.RELEASE_APP_PRIVATE_KEY }}

- uses: actions/checkout@v6
  with:
    token: ${{ steps.app-token.outputs.token }}   # 用它推的 tag 才會觸發 CI

對照：開 PR 的那幾支 workflow 用 GITHUB_TOKEN 就夠。副作用剛好合理：自動 PR 不會自己跑 CI，等人 merge 才跑。

版本 / 全貌

一次建置的身分由三個數字組成

數字從哪來誰決定例
version name pubspec.yaml 的 version: 人，或 bump workflow 自動 PATCH +1 1.4.2
tag push tag workflow 依版號推算 workflow 自動命名 v1.4.2
build number 獨立分支上的月計數器 CI 自動遞增 260700015

CI 不對版號做任何轉換：兩條線讀同一個 pubspec.yaml 欄位，差別只在 tag 前綴。產物名稱把三者組起來，尾綴是 github.ref_name（推 tag 時就是 tag 名）。

myapp-1.4.2+260700015-v1.4.2.apk
版本 / tag 命名

同版本再發一次，後綴從 -2 開始

workflow 會先列出遠端所有符合的 tag，算出這是第幾次發版，再決定 tag 名。後綴數字對齊「第 N 次」的口語，所以沒有 -1。

# 版號停在 1.4.2，重複跑同一支 workflow
第 1 次   v1.4.2      ← 純版號，base tag
第 2 次   v1.4.2-2
第 3 次   v1.4.2-3

# 判斷方式：列出遠端 tag，找出最大的 -N
git ls-remote --tags origin "refs/tags/$BASE_TAG*"
  • 版號不變，但 build number 會遞增，所以 TestFlight 與 App Distribution 都視為新的建置
  • dev 線直接重跑即可，沒有額外關卡
  • prod 線base tag 已存在時會直接失敗，除非明確勾選確認重發
版本 / build number

年月加當月流水號，九位數

260700015

2026 年 7 月的第 15 次正式建置

為什麼這樣切

年月在前，保證跨月與跨年都遞增（2701… > 2612…），商店只接受遞增的 build number。

每月從 1 重新計數，人眼能直接讀出這個建置是哪個月出的。

為什麼是九位

Android 的 versionCode 上限是 2100000000。九位數最大 991299999，永遠不會撞到天花板。

也就是這個格式可以一路用到 2099 年都不需要換算法。

版本 / 兩種建置

發版建置與 PR 建置的號碼機制不同

產生 build number 的 action 收一個 persist 參數，值直接來自派發閘門的結果，兩條路徑完全分開。

發版建置 / persist = true

觸發推 tag
來源計數器 +1
寫回會，更新計數器分支
號碼YYMM + 補零計數
260700015

PR / 分支 / 手動 / persist = false

觸發push 分支、開 PR、手動觸發
來源GITHUB_RUN_NUMBER 取五位
寫回不會，完全不碰計數器
號碼YYMM + run number
只為讓建置跑得完

所以計數器的數字等於真正發出去的次數，PR 驗證跑幾百次都不會影響它。

版本 / 計數器

計數器存在一個孤兒分支上

# 這個分支與主線程式碼完全隔離，只放一個檔案
build-history.json
{ "production": { "2026-07": 15 }, "development": { "2026-07": 8 } }

# 每次寫入都是 amend + force push，分支永遠只有一個 commit
git commit --amend -m "Build counter: production 2026-07 = 15"
git push --force origin build-metadata
為什麼需要排隊 因為用 force push，兩個 job 同時寫會互相蓋掉。呼叫端的 job 掛 concurrency group 且 cancel-in-progress: false，讓它排隊而不是取消。
環境 / 入口

所有環境差異都從一個 JSON 出發

每個環境一份 JSON，是唯一的來源。CI 只做一件事：把對應那份餵給 Flutter。

# 建置前先注入 git hash 等資訊，產出最終的 dart-define.json
GIT_HASH=$(git rev-parse --short HEAD)
jq '. + {GIT_HASH: $git_hash}' "$ORIGINAL_CONFIG" > build_config/dart-define.json

flutter build apk --release --dart-define-from-file=build_config/dart-define.json \
  --build-name=1.4.2 --build-number=260700015
  • Dart 端讀得到這些值，Android 的 Gradle 也讀得到，所以 bundle id 與資源能跟著切
  • iOS 讀不到，需要另一支 script 轉成 xcconfig
  • 最終產出的 dart-define.json 在 .gitignore 裡，它是產物不是設定
環境 / bundle id

一個 base，一個後綴

兩個平台的 bundle id 都不是各寫死一份，而是同一個 base 加上由環境決定的後綴。這也是兩個 app 能同時裝在一台機器上的原因。

com.example.myapp.dev
com.example.myapp   

後綴在兩個平台叫同一個名字 APP_CONFIG_SUFFIX，只是抵達的路徑不同。

環境 / 後綴怎麼到位

Gradle 直接讀，Xcode 要人翻譯

Android / Gradle 讀 dart-defines

// build.gradle.kts：解 base64 找 ENV
dartDefines.split(",").forEach { entry ->
  val decoded = String(
    Base64.getDecoder().decode(entry))
  // ENV=development → 設定整組變數
}

defaultConfig {
  applicationId = "com.example.myapp"
  applicationIdSuffix =
    dartEnvironmentVariables["APP_CONFIG_SUFFIX"]
}

同一組變數也決定 app 名稱與通知頻道文字。

iOS / script 產生 xcconfig

# script 寫出 xcconfig
cat > ios/Flutter/AppConfig.xcconfig <<EOF
APP_CONFIG_SUFFIX=.dev
APP_CONFIG_NAME=MyApp [DEV]
EOF

# pbxproj 裡寫的是變數，不是值
PRODUCT_BUNDLE_IDENTIFIER =
  "com.example.myapp$(APP_CONFIG_SUFFIX)"

script 反過來從 pbxproj 抓 base id，只有一個真實來源。

環境 / 檔案就位

有些東西沒有變數可用，只能把檔案複製到位

變數能解決的（bundle id、app 名稱、icon 名稱）就用變數。剩下的只能在建置前把對應檔案複製成固定檔名，讓下游工具讀到。

要換的東西誰做怎麼做
Android Firebase 設定 Gradle task 把 config/{dev,prod}/google-services.json 複製到 app 根目錄，掛在 google-services 處理之前
iOS Firebase 設定 shell script 把 config/{Dev,Prod}/GoogleService-Info.plist 複製到 Runner/
iOS Launch image Xcode build phase 把 LaunchImage-{Dev,Prod}.imageset 複製成通用的 LaunchImage.imageset
Android App icon 不用複製 Gradle sourceSets 直接把 src/{dev,prod}/res 疊進 res.srcDirs
Launch image 為什麼要多這一步 LaunchScreen.storyboard 無法引用 xcconfig 變數，只能讓它固定引用 LaunchImage，再由 build phase 把對的圖搬進那個名字。
環境 / Firebase

兩套獨立專案，靠 bundle id 對上

兩個環境接的是兩個完全獨立的 Firebase 專案，資料、Crashlytics 與推播設定都分開。設定檔裡寫著「我是給哪個 bundle id 用的」，對不上就不給用。

設定檔裡寫著  "package_name": "com.example.myapp.dev"
建置算出來的  applicationId + Suffix = "com.example.myapp.dev"
                                       ↑ 必須一模一樣，否則 Android 直接建置失敗
  • 要再加環境，架構撐得住：所有環境差異都收斂成「一個 ENV 值 ＋ 一組按環境命名的目錄」，照樣式新增就好
  • 但有兩處分支要各補一個 case：Gradle 的 when (ENV) 與 iOS script 的 case，還要先去 Firebase Console 註冊新 bundle id 才拿得到設定檔
  • iOS 的 dSYM 上傳也吃這份設定檔，環境錯了符號會傳到另一個專案，線上當機就查不到來源
進階 / 分流

推了 tag 之後，staging 會發生什麼

兩支自動 workflow 監聽同一個 tag pattern，用兩個獨立問題把情境切成四種，彼此互斥。

情境tagmain 有新 commit結果
A 真 hotfixv1.4.3有把 main 併回 staging，並 bump 版號
B 重發加修正v1.4.2-2有只併回，不 bump
C 純重打包v1.4.2-2沒有兩支都跳過
D 正常發版v1.4.3沒有只 bump staging 版號
 
# 判斷用的兩個訊號
git rev-list --count origin/staging..origin/main --no-merges   # 要不要併回
[[ "$TAG" =~ -[0-9]+$ ]]                                       # 要不要 bump

把「要不要併回」與「要不要 bump」拆成兩個獨立問題，是這段設計最關鍵的一步。四種情境就從兩個布林值自然長出來，不需要寫四條規則。

這個判定有個前提 rev-list --count 比對的是 commit SHA、不是內容，而 rebase 與 squash merge 都會重寫 SHA，於是正常發版會被誤判成有 divergence。要嘛把 staging → main 限制成 merge commit，要嘛改用 --cherry-pick --right-only 以 patch-id 比對，後者對兩種 merge 模式都免疫。
進階 / iOS 簽章

iOS 簽章走臨時 keychain

自架 runner 的 keychain 是長期狀態，一旦被污染，之後所有 iOS 建置都會出問題，而且很難查。所以整個簽章流程都在臨時 keychain 裡完成。

keychain initialize                       # 建立臨時 keychain 並設為預設

app-store-connect fetch-signing-files "$BUNDLE_ID" \   # 用算好的 bundle id 抓
  --platform IOS --type IOS_APP_STORE \
  --certificate-key=@file:$CERT_KEY_PATH \
  --strict-match-identifier --delete-stale-profiles --create

keychain add-certificates --certificate "$RUNNER_TEMP/certificates/*.p12"
xcode-project use-profiles --export-options-plist=$RUNNER_TEMP/export_options.plist

flutter build ipa --release --export-options-plist=...

keychain use-login                        # if: always() —— 失敗也要還原
  • 還原那步掛 if: always()，所以建置失敗也不會把預設 keychain 留在臨時的那個
  • 憑證與 private key 都寫在 $RUNNER_TEMP，收尾一併刪掉
  • 這裡用的是 Codemagic CLI tools，它把 keychain 與憑證的處理包成幾個指令
收尾

可以帶走的幾個設計原則

  1. 讓分支決定一切。一條線一組環境、一個 tag 前綴、一個 Firebase 專案，不要有第三種組合。
  2. 把「建置」與「派發」分開。推分支只驗證，只有 tag 會真的送出去，也只有 tag 會消耗建置編號。
  3. 版號只留一個來源。其他數字（tag 名、建置編號）都從它推導，不要讓人有機會填錯第二個地方。
  4. 環境差異收斂成一個入口。能用變數的用變數，不能的就在建置前把檔案複製到位，並把產物都放進 gitignore。
  5. 把複雜情境拆成獨立的布林值。四種發版情境是兩個問題的組合，不是四條規則。
  6. 不要污染 runner 的長期狀態。臨時 keychain、臨時 SSH key，並且在失敗路徑上也要還原。
