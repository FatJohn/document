# 10/15｜初級工程師如何 AI 賦能的翻寫一個跟自己年紀差不多大的框架

讀者：正在處理 legacy modernisation、原始碼不完整或領域規則深的工程團隊

型別：說明

## 核心摘要

這場最值得學的是驗證策略，而不是「用 AI 重寫老系統」。第一階段先把舊系統當黑箱，守住行為等價與資料不變；第二階段才談重新設計與擴充。AI 只是讓分析、實作與 review 的角色可以拆開，不能替代對舊系統行為的觀察與比對。

## 重點

- 先建立可重現的舊系統與新系統測試環境，對相同輸入送出相同請求，再比較 response 與資料庫狀態。
- 第一階段限制資料變動，避免「翻寫」同時變成資料遷移、規則修改與架構重設計，讓差異無法定位。
- 驗證可拆成三條線：新系統是否符合新規格、邏輯是否與舊系統及文件一致、相同輸入是否得到相同結果與資料狀態。
- 工作流以不同角色分擔：PM 釐清為什麼與驗收標準，架構角色盤點現有慣例與測試，實作者改動，test-reviewer 檢查測試是否真的增加信心，reviewer 檢查工程風險，QA 做系統驗收。
- 測試 review 要防止 AI 為了綠燈修改測試或只追求 coverage；要看測試語意、失敗時是否能揭露錯誤，以及是否涵蓋回歸風險。
- 文件太長時，讓 AI 一次問一個問題、一次處理一個 concern，比要求它一次消化所有背景更容易保留人的確認。
- 一般 Skill 與隔離上下文的 agent skill 可以分工：前者提供工作能力與背景，後者適合不需污染主上下文、只需結果的重複 review；hook 則用來強制確定性的提醒。

## 可以學什麼

黑箱翻寫可以先做一個最小的差異報告：

```text
輸入 request
  → 舊系統 response / DB 狀態
  → 新系統 response / DB 狀態
  → 正規化非本質差異
  → 報告欄位、值、錯誤與副作用差異
```

真正要先設計的是比較規則：時間戳、流水號、排序、外部副作用、資料重置與敏感欄位如何處理。這些沒有定義清楚，機械比對只會產生大量噪音。

## 我的補充與反思

我把這場理解成一個團隊翻寫二十年以上系統的經驗分享。這種案例可以提供 insight，但我沒有聽完整場，也不覺得它的翻新方法能直接泛化到其他 legacy 系統。

對我而言，它比較適合拿來觀察「哪些驗證策略值得借用」，而不是直接學一套完整的方法論。資料、外部依賴、領域規則與失敗成本不同時，工作流仍需要重新設計。

## 這場的限制

這是 12 場中最接近可落地驗證策略的案例，但仍不能直接照做。公開資料沒有完整交代資料正規化、測試資料生命週期、外部依賴隔離、失敗差異處理與安全邊界；部分舊技術、工具與 agent 名稱也有待確認。官方摘要則明確支持 PM → 架構 → 實作 → 測試審查 → 程式審查 → QA 的角色拆分方向。

## 公開資料補充欄位

- 講者簡報：待官方來源加入；補上舊新系統拓撲、比對欄位與 subagent 交接文件。
- 官方錄影：待官方來源加入；確認黑箱測試、DB 比對與 QA fork context 的實際示範。
- 重整優先：先用一個低副作用、可重置的 legacy use case 試作差異報告，再擴大範圍。
