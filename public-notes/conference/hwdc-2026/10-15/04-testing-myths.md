# 10/15｜AI 時代下測試的迷思——為什麼綠燈越多，品質卻沒有變好

讀者：想評估 AI 生成測試是否真的提高信心，而不是只提高測試數量的工程團隊

型別：說明

## 核心摘要

AI 讓產生 code 和 test 都變快，卻沒有讓測試自動變得有意義。綠燈只代表這次檢查通過；它不能證明需求正確、測試有抓到商業風險，或系統沒有未探索的錯誤。品質的瓶頸從「寫不出測試」移到「判斷測試是否值得保留」。

## 重點

- AI 容易生成大量相同等價類、只驗證非空或呼叫成功、反映錯誤實作的測試；它未必知道真正的商業邊界與互動序列。
- coverage 只能表示程式行是否被執行，不代表斷言有意義，也不代表風險被覆蓋。
- 測試包含 checking 與 exploring：前者檢查已知條件，後者要透過示範、團隊探索、pair／mob testing 或其他方式發現未知問題。
- BDD 不是一個人把需求轉成 prompt 或測試；共享需求與範例的討論本身就是品質活動。
- AI 生成的測試至少要經過編譯與執行、負向或 mutation 檢查、穩定性、非重複性與人工語意 review；只有能增加信心的測試才留下。
- AI 可能改 production code 或測試本身來取得綠燈，因此要把「誰改了什麼」與「為什麼這個綠燈代表需求成立」納入 review。
- 測試可以證明某個 bug 存在，不能證明沒有 bug；人工 mutation 是開始理解測試強度的低門檻方法。

## 可以學什麼

把測試 review 改成四個問題：

1. 這個測試失敗時，會揭露哪個具體錯誤？
2. 它是否真的涵蓋一個不同的風險或等價類？
3. 把 production code 做一個小 mutation，它會不會失敗？
4. 測試是依需求與行為寫的，還是只是照著既有實作鏡像出來？

這場最實用的下一步不是追求更多測試，而是挑一條重要流程做一次 mutation 與探索式測試，觀察既有綠燈到底提供多少信心。

## 我的補充與反思

前面談測試迷思的部分，對有經驗的工程師來說比較像已知用火：綠燈多不等於品質高，coverage 也不等於信心。對我而言，後段提出的解法比較有價值，雖然我沒有記住完整細節，也希望能有講義可以重新對照。

其中一些術語與方法確實有技術深度。我曾把類似的想法套用到一個 SDK 專案，補上不足的測試；因此這場對我最值得學的不是前面的提醒，而是最後如何把測試判斷轉成可以執行的工程方法。

## 這場的限制

這場提供的是測試判斷框架，不是一套 AI test generator 的工具教學。演講中若有 test 數量、通過率或改善幅度，應視為案例，除非補到公開原始資料，否則不做普遍化。

## 公開資料補充欄位

- 講者簡報：待官方來源加入；補上 mutation、等價類、探索式測試與範例。
- 官方錄影：待官方來源加入；回看示範中測試如何被判定為無效或重複。
- 重整優先：在 CI 中加入一個可控的 mutation 或負向案例，並保留測試語意 review，而不是只提高 coverage 門檻。
