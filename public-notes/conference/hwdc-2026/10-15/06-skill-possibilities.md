# 10/15｜挖掘技能的全新可能性 <!-- allow-time-word -->

讀者：已經使用多個 AI Skill 或 Agent、需要處理路由、重疊、失敗與維護的人

型別：說明

## 核心摘要

Skill 不只是 prompt 的集合，而是一種需要路由、組合、評估、演化與治理的工程資產。當技能變多，真正困難的問題會變成：什麼意圖該走哪個模組、模組如何協作、失敗如何回退、如何證明完成，以及誰負責批准變更。

## 重點

- 路由型 Skill 可以提供一個領域入口，內部分派到較小的子模組；路由依使用者意圖、任務條件、當下狀態與可用能力決定。
- 子模組要有清楚的輸入／輸出與責任，流程可以分支，但每個分支都要有前置條件、後置檢查與失敗回退。
- 同一領域的 Skill 可以融合，但融合前要比較新增能力、重疊能力與衝突規則；不能只把兩段文字接在一起。
- 演化應從失敗案例與反例開始。人先標記哪裡不符合需求，AI 再提出修正，修正後把案例留成回歸評估。
- 可確定的動作要用確定性程式或結構檢查承擔；自然語言 checklist 可能只會讓模型自我宣稱「都完成了」。
- 一個高控制力的 Skill 至少要說清楚何時觸發、要做什麼、禁止什麼、失敗怎麼處理、衝突如何決定，以及完成的證據是什麼。
- Skill lifecycle 不只包含建立與測試，也包含評估、融合／拆分、演化、安全檢查、封裝發布、遷移、淘汰與 agent 治理。
- 產生投影片、圖表或其他視覺產物時，應先 render，再做視覺檢查；人類 review 不能退化成無條件蓋章。

## 可以學什麼

可以把 Skill 的設計審查成六個問題：

1. 觸發條件是什麼？什麼情況不該觸發？
2. 輸入、輸出與責任邊界是什麼？
3. 哪些步驟可以交給模型，哪些步驟必須由程式檢查？
4. 失敗、逾時、能力不足或模組衝突時怎麼回退？
5. 如何記錄反例、評估回歸與批准演化？
6. 什麼證據可以證明任務完成，而不是只有模型回報完成？

這六問能把「Skill 很靈活」轉成「Skill 有可檢查的控制面」。

## 我的補充與反思

這場是我在 Day2 聽到最有明顯技術感的一場。SkillOps 是我新聽到的名詞。
[SkillOps Atlas](https://skillops-studio-atlas.allanyiin.chatgpt.site/) 不只談概念，也提供路由觀念、情境 Prompt、Skill 套件與生命週期內容，值得拿一個小範圍試用。

我看到的核心連接是：路由型 Studio 先從入口理解意圖，再依 context、證據與風險選擇模組，最後協調輸入、交棒、狀態與驗證。這和我全域規則裡的 `dispatch` 有相似結構，但我的版本是治理規則，不是 Skill runtime。

我不會把所有全域規則直接轉成 Skill。比較合理的拆法是：

- 不可違反的治理原則留在全域規則。
- 有固定輸入、產出、限制與驗證的重複工作，轉成一般 Skill。
- 根據意圖、證據與風險選擇模組的部分，整理成 router 或入口 Skill。
- 失敗案例、負向案例與完成證據，轉成 Skill 的評估與回歸資料。

這個網站把 Skill 的生命週期延伸到建立、驗證、發布、觀測、演化與退場。
它也提醒我：Skill 化不只是把規則換成另一個檔案，而是要補上責任、路由、證據與維護方式。

## 這場的限制

概念與生命週期方向很值得留，尤其是 routing、fallback、反例演化與完成證據；但示範平台、相容性限制與部分專名需要官方投影片或錄影才能精確引用。這場提供的是設計框架，不是現成的 Skill runtime 或跨平台規格。

## 公開資料補充欄位

- 講者簡報：待官方來源加入；補上 routing、fusion、evaluation 與 lifecycle 的正式圖例。
- 官方錄影：待官方來源加入；確認 demo 的輸入／輸出、fallback、評估與視覺檢查實作。
- 重整優先：挑一個已有多個 Skill 的領域，先建立觸發、衝突、失敗與完成證據的測試案例，再談融合或演化。
