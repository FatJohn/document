# 10/14｜讓 Agent Skills 介入你的軟體開發的工作流

讀者：想把軟體工程方法封裝成可重複 AI 工作流的開發者與團隊

型別：說明

## 核心摘要

Skill 的價值不在於多寫一段 prompt，而在於把需求釐清、領域模型、架構邊界、測試設計與實作順序變成可重複的工作方法。AI 越容易產出程式，越需要先決定它只能在什麼範圍內工作，以及要用什麼證據判斷結果。

## 重點

- 給 AI 的任務要控制粒度；類別、方法或一個明確 use case 通常比「做完整產品」更容易驗證。
- 需求不能假設 AI 會自行補齊。產品需求、客戶需求與隱含的領域規則，仍要由人挖掘、澄清並決定優先順序。
- 先表達領域模型、依賴方向、架構限制與測試設計，再請 AI 實作；domain model、dependency injection、UML 或 sequence diagram 都是讓邊界具體化的工具。
- Skill 可以把團隊規則封裝成流程，例如先產出 use case 與流程圖，再產出 domain 類別，最後才進入實作與測試。
- 租車案例的重點不是租車本身，而是用 use case 把範圍拆成選車型、選租期、計租金、確認租車等行為，避免 AI 擴張到不相干功能。
- 大型規格包不一定比較好；輕量、可讀、能在每個小任務中被驗證的規格，往往更適合日常協作。

## 可以學什麼

可以把每個 Skill 寫成「輸入—限制—產出—驗證」：

| 部分 | 要回答的問題 |
|---|---|
| 輸入 | 這個任務已知什麼，還缺什麼？ |
| 限制 | 不得跨過哪些 domain、架構或資料邊界？ |
| 產出 | 要交付規格、圖、程式、測試，還是決策紀錄？ |
| 驗證 | 如何知道產出符合需求，而不是只有格式正確？ |

這個框架能讓 Skill 從「提示詞收藏」變成可以被 review、測試與改進的工程資產。

## 這場的限制

工程實作潛力高，但公開內容與逐字內容沒有提供可完整重現的 Skill 檔案、命令、輸出或量測。講者自訂流程與工具名稱不能直接當成既有標準；成效類主張也不應脫離其案例脈絡。

## 公開資料補充欄位

- 講者簡報：待官方來源加入；補上 Skill 的正式結構、範例與工作流圖。
- 官方錄影：待官方來源加入；回看 domain model、use case 與實作示範的實際順序。
- 重整優先：選一個小型 use case，將「輸入—限制—產出—驗證」寫成可試跑的 Skill，再檢查是否真的減少返工。
