# 10/14｜讓工程師失業的 N + 1 道陰影

讀者：想讓 AI 產碼仍然受規格、測試與工程判斷約束的開發團隊

型別：說明

## 核心摘要

AI 沒有取代完整 SDLC；它只是讓「規格是否清楚、規格是否和實作同步、審查是否有抓到風險」變得更關鍵。這場最值得留下的概念，是把規格當成跨人、跨模型、跨 Agent 的交接介面，而不是一次性給模型讀完就丟掉的 prompt。

## 重點

- SDD 可以理解成先有規格，再由規格導出測試與程式；但規格與實作必須同步，否則只是把過時文件換成另一種過時文件。
- 規格不必有唯一格式，卻要足以讓不同工具或不同 AI 接手時，不把目標做偏。需求、邊界、驗收條件與不做什麼，都應能被交接。
- 實作中若改了需求，例如介面行為或視覺細節，應把變更回寫規格，避免 specification drift。講者以 `ingest` 類型的 Skill 說明這個回寫方向。
- 人類不必逐行閱讀所有 AI 產碼，但要看 diff、敏感流程與高後果區域，例如金流、權限與資料異動；本機操作與副作用也應保留明確授權點。
- 規格可以幫助工作跨模型或供應商接續，但直接搬運另一個 Agent 的完整上下文，不等於成功交接；摘要、決策與驗收條件仍需要整理。

## 可以學什麼

把規格設計成「可以被接手」的工件，至少要能回答：

1. 這次要解決什麼問題，成功長什麼樣子？
2. 哪些行為、資料與邊界不能改？
3. 哪些變更需要人停下來確認？
4. 實作改變後，哪一份規格、測試或決策紀錄要同步更新？

這比追求一套神奇的規格格式更重要。對 legacy 系統尤其適合先補一小段、驗證一小段，再逐步擴充，而不是先要求 AI 逆向產出一份「完整且可信」的全系統規格。

## 我的補充與反思

這是 Day1 最有趣、也最有幫助的一場。它讓我看到 SDD 不只是「先寫規格再寫程式」，還包含規格與實作同步、交接、人工停點與回寫。

講者提供了一份簡單的 [SDD 流程 Gist](https://gist.github.com/kaochenlong/27ade9a6218244c2584777fa276d1214)。我覺得它很適合被整理成自己的 Skill，但 Skill 不應只有一段 prompt，而要把每個階段的輸入、產出、檢查與交接格式固定下來。

我會先把它轉成這種工作流：

1. 釐清問題、範圍與驗收條件。
2. 產出規格與設計，先讓人確認方向。
3. 拆成可以獨立完成與檢查的小任務。
4. 實作、測試與 review。
5. 把實作中確認的需求變更回寫規格。

這樣 SDD 才會從一份文件變成自己的開發流程，也能和 05 的 Skills 觀念接起來。

## 這場的限制

工程方法值得學，但公開資料不足以重建講者的 GUI、Skill、規格檔格式、測試策略或同步演算法。部分縮寫與工具名稱仍待官方資料確認，不能直接當作正式工具選型或標準方法引用。

## 公開資料補充欄位

- 講者簡報：待官方來源加入；補上 SDD 層次、規格範本與同步流程。
- 官方錄影：待官方來源加入；確認 `ingest` Skill 的正式名稱、輸入與輸出。
- 重整優先：把「規格作為交接介面」轉成一份可實際套用的 issue／PR 範本，並補出人類審核停點。
