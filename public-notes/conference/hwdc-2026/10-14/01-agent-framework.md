# 10/14｜自己刻 Agent 框架：最難的不是呼叫 LLM

讀者：想把 Agent 從 demo 帶進可靠服務的工程師與架構師

型別：說明

## 核心摘要

這場真正談的不是如何呼叫 LLM，而是如何把 LLM 放進一個可控的系統。模型可以負責推理與選擇，但敏感資料、權限、不可接受的錯誤、固定格式輸出與完成證據，應交給系統規則和確定性元件承擔。

## 重點

- 工具結果不應整包回灌模型。系統應先保存完整資料，再依任務過濾 PII、無關內容與過大的 context，只把推理需要的資料或 reference 交給模型。
- 固定格式的報告、日期計算、退款判斷、權限與其他「錯一次也不能接受」的決策，不應只靠 prompt 或 Skill 約束；應以 report builder、程式檢查、gate 或 guardrail 固定下來。
- 驗證要拆成兩條線：產出是否符合需求，以及 Agent 的執行軌跡是否符合規則。前者可以由模型輔助判斷，後者則應檢查 tool call、trace、權限與順序。
- Human-in-the-loop 不只是最後按同意。它可以用來確認 Agent 是否理解任務；對有副作用的動作，批准後也要重新檢查當下狀態。
- Skill 的修正可能讓其他情境退化。應保留固定設定、多情境與重複執行的評估，並把線上事故轉成回歸案例。

## 可以學什麼

最值得帶走的是「把規則放進正確的承載物」：

| 風險或需求 | 比較適合的承載物 |
|---|---|
| 模型要理解的上下文 | 最小必要資料、reference、明確輸入格式 |
| 固定格式或計算 | 確定性程式元件 |
| 權限與不可接受錯誤 | gate、guardrail、程式檢查 |
| 執行是否合規 | trace／tool-call 檢查 |
| 既有情境不可退化 | 固定評估集與回歸測試 |

這個分工比「再寫一段更長的 system prompt」更能直接轉成架構決策與驗收條件。

## 我的補充與反思

這場點出了很多 Agent 的痛點，卻沒有讓我看見如何把它們組成完整的 AI flow。

我期待補上的總圖至少要回答這條路徑：

1. 先定義目標、範圍與成功條件。
2. 選擇這一輪真正需要的 context 與 reference。
3. 讓 Agent 透過 tool loop 執行工作。
4. 用程式檢查、權限 gate 與 guardrail 擋住不可接受的錯誤。
5. 分別檢查產出品質與執行軌跡。
6. 在副作用操作前保留人的判斷點。
7. 把 trace、失敗案例與成本回饋到下一輪改善。

這些元素各自都合理，但少了這張組裝圖，我仍然不知道該從哪一層開始、每一層由誰負責，以及它們如何接成一個可運作的 AI flow。對我來說，這是本場最大的缺口。

## 這場的限制

技術方向很值得學，但不能直接複製完整框架。資料模型、授權模型與 reference 的生命週期仍要另行設計。trace schema、評估資料集與通過門檻也需要補上。本整理無法確認的 SDK、模型型號與評估術語，不硬還原成正式名稱。

## 公開資料補充欄位

- 講者簡報：待官方來源加入；補上正式架構圖、元件名稱與限制。
- 官方錄影：待官方來源加入；回看 context 過濾、trace 驗證與 human-in-the-loop 示範。
- 重整優先：確認「產出驗證」與「軌跡驗證」的實際工具，以及講者提到的評估方法是否有明確門檻。
