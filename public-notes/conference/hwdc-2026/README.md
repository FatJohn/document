# Hello World Dev Conference 2026：Session 重點整理

讀者：參加 Hello World Dev Conference 2026、想快速回顧 10/14 與 10/15 議程的人

型別：說明

## 這份整理先給的結論

這 12 場不是每一場都在教一個可以直接複製的技術方案。

技術方法最完整的場次有以下幾場：

- 自己刻 Agent 框架
- 讓工程師失業的 N + 1 道陰影
- 讓 Agent Skills 介入工作流
- 從一人 AI 工作流到團隊工程系統
- 初級工程師如何 AI 賦能地翻寫 legacy 系統
- AI 時代下測試的迷思
- 挖掘技能

這些場次共同指出：AI 產出越快，規格、邊界、檢查、回歸與責任越不能省略。

「動態專注」、「AI 導入之後的團隊角色」、「買完 AI 工具，然後呢？」與「每個人都有 AI，為什麼團隊還是這麼慢？」比較像工作方法、組織治理與責任重新分配的分享。它們有值得帶走的觀念，但不能只靠演講內容直接推導出一套完整制度。

「AI Agent 時代的真正專業」主要是定位與態度的反思。若期待具體框架、工具或測試方法，這場的可操作細節相對有限；這不是缺點，只是它解答的是另一個問題。

## 閱讀方式

每場筆記都分成四層：

- 核心摘要：這場真正想處理的問題。
- 重點：依內容整理出的主張與方法。
- 可以學什麼：哪些能轉成工作習慣、設計原則或驗收條件。
- 這場的限制：哪些是案例、態度或尚待公開材料補足的部分。

「講者主張」與「整理者判斷」刻意分開。講者在現場提到的數字、工具名或成功案例，若沒有公開原始資料支持，只保留為案例脈絡，不當作普遍結論。逐字內容中無法確認的專有名詞，也不以猜測補成正式術語。

## 兩天的共同主線

可以把 12 場收斂成一條工程問題鏈：

```text
需求與目標
  → 規格、領域語言、架構邊界
  → 小增量實作與可重複的 Skills
  → 確定性檢查、測試、review、QA
  → 團隊共享脈絡與治理
  → 以交付結果而不是產出速度判斷價值
```

如果只拿走一個原則，就是：不要把「AI 很快寫出東西」誤認成「系統已經能可靠交付」。

## 公開資料補充欄位

| 欄位 | 查核狀態（2026-10-16） | 重整時要做的事 |
|---|---|---|
| 講者簡報 | 各場共筆尚未提供可供核對的簡報連結 | 以投影片的正式術語、圖表、程式碼與限制修正筆記 |
| 官方錄影 | 議程／共筆入口尚未提供官方錄影連結 | 回看示範、確認 ASR 不確定的專名與完整上下文 |
| 共筆 | 已列在各場筆記的來源區 | 對照講者原文、補上引用與相關資源 |
| 成效數字 | 只視為講者案例，未作普遍結論 | 有原始資料時補上口徑、樣本與適用範圍 |

這些欄位不是預設結論；它們只是讓官方材料到位後，可以在原場次檔案內增補，而不用重新建立整理架構。
